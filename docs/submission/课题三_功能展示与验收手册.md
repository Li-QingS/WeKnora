## 三、功能一：评测任务持久化

### 用户看到什么

RAG 评测不再只存在后端内存。页面刷新或服务重启后，历史运行、状态、错误、指标、配置快照仍可查询。不同租户只能访问自己的评测记录。

### 关键实现

- `evaluation_runs` 保存数据集、任务状态、开始时间、进度、错误、指标、`config_hash` 和 `config_snapshot`。
- 配置快照记录数据集 SHA-256、样本数、模型标识、分块参数和版本信息。
- 后台任务具有心跳、恢复和终态处理，避免重启后永久停留在“运行中”。
- PostgreSQL 与 Lite/SQLite 都有对应迁移和升级测试。

### 验收步骤

1. 在评测中心选择数据集、Embedding、问答、Rerank 和分块参数。
2. 点击“开始评测”，观察样本进度。
3. 完成后刷新浏览器，重新打开相同运行。
4. 重启后端，再次查看历史详情。
5. 核对运行 ID、数据集、样本数、状态、配置指纹、模型快照和四类指标。

### 通过标准

- 刷新和后端重启后记录不丢失。
- 成功、失败、中断状态及错误信息可追溯。
- 同一配置与数据集产生稳定的 `config_hash`。
- Viewer 可以查看，只有具备相应权限的用户可以发起或删除。

### 证据位置

`docs/specs/evaluation-persistence/`、`docs/specs/evaluation-runner/`、`docs/api/evaluation.md`。

## 五、功能三：RAG CI 质量回归门禁

### 用户看到什么

代码修改导致 Recall 等指标低于门槛时，CI 直接失败，并指出指标、当前值、基线值、下降幅度和阈值，而不是只显示笼统错误。

### 本地验收

```bash
make -C cli build

./cli/bin/weknora eval compare \
  --result evaluation/fixtures/evaluation-result-pass.json \
  --baseline evaluation/baselines/demo.yaml
echo $?

./cli/bin/weknora eval compare \
  --result evaluation/fixtures/evaluation-result-degraded.json \
  --baseline evaluation/baselines/demo.yaml
echo $?
```

预期第一组返回 0；第二组返回 2，并列出 Recall 等退化指标。配置或数据集不一致返回 3，防止用不同“考卷”强行比较。

| 正常基线 | 34238633896 | success | Recall 1.0000，比较器退出 0 |
| 人为降低 Recall | 34239374350 | failure | Recall 1.0000 → 0.6000，低于 0.8000 门槛，退出 2 |
| 恢复正常 | 34239666469 | success | 场景恢复后重新通过 |

## 七、功能五：Embedding 缓存

### 解决的问题

文档上传、重解析或重建索引时，相同 Chunk 使用相同模型会重复生成向量。本成果加入 SQL 持久缓存，使向量可跨进程重启、多实例复用，并在应用进程中处理格式漂移和并发冷请求。

### 技术方案

1. 缓存身份包含租户、模型、向量维度、非敏感模型配置签名和规范文本哈希，避免跨租户、跨模型或跨向量空间误用。
2. 保守规范化只处理 BOM、Unicode NFC、CRLF、首尾空白和行尾水平空白，不破坏正文内部空格、Markdown 或代码缩进。
3. 新键未命中时兼容旧精确键，并进行惰性提升，无需清空历史缓存。
4. Batch 内相同文本和格式等价文本只向 Provider 发送一次。
5. 同进程并发相同冷请求共享一次 Provider 结果；等待者分别响应自己的 Context 取消。
6. 缓存读写失败时降级调用 Provider，不阻断文档入库。

### 为什么使用 SQL

SQL 能兼容 PostgreSQL 和 Lite/SQLite，支持跨重启、多实例共享。当前 Redis 同时承载队列与流，没有为大向量设置独立内存预算、TTL 和淘汰策略，直接写入共享 Redis 会增加内存挤压风险。本版本采用“SQL 持久层 + 进程内瞬时合并”；未来只有在监控证明 SQL 读取成为瓶颈后，才适合增加具有独立容量的 Redis L1。

### 实测效果

固定数据取自项目 EnterpriseRAG：85 条语料输入和 50 条查询输入，共 135 个基础输入；依次执行冷导入、完全相同重放、带 BOM/CRLF/行尾/首尾空白漂移的重放。

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 总请求 | 405 | 405 | 相同工作量 |
| 缓存命中 | 135 | 270 | +135 |
| 缓存命中率 | 33.33% | 66.67% | **+33.33 pp** |
| Provider 输入 | 270 | 135 | **减少 50.00%** |
| 32 个相同并发冷请求的 Provider 调用 | 32 | 1 | **减少 96.875%** |
| 16 个并发双输入 Batch 的 Provider 调用 | 16 | 1 | **减少 93.75%** |

这些数字是固定工作负载的可复现对照，不代表未来任意线上流量都会获得相同比例。

## 八、功能六：Wiki Prompt Cache 优化

### 解决的问题

Wiki 页面生成和引用抽取会在同一轮中重复发送大量固定规则、文档上下文和候选节点。旧 Prompt 把固定与变化内容混在一起，服务商难以稳定复用缓存。

### 通用方案

- 业务层通过 `PromptCacheBreakpoint` 声明稳定前缀结束位置，不检查模型名称。
- 页面生成缓存系统规则、共享文档上下文和编辑规则；页面元数据、已有页面和新增证据保留为动态尾部。
- 引用抽取缓存规则和候选实体/概念；本批 chunks 保留为动态尾部。
- Anthropic 使用 content block 缓存点；百炼兼容端点使用稳定/动态同角色消息；OpenAI/Azure/OpenRouter 使用稳定前缀指纹作为缓存路由信息；不支持的 Provider 保持原调用。
- 相同租户、模型、用途和前缀的并发首请求先预热，再放行跟随请求。

### 9 月 8 日与最终版本实测对比

使用同一知识库、同一文档和同一模型连续运行。统一口径为 `cache_read_tokens / prompt_tokens`。

| 范围 | 9 月 8 日冷运行 | 最终冷运行 | 冷提升 | 9 月 8 日热运行 | 最终热运行 | 热提升 |
|---|---:|---:|---:|---:|---:|---:|
| 全部 Wiki 调用 | 14.78% | 17.19% | **+2.41 pp** | 16.46% | 24.97% | **+8.51 pp** |
| 页面生成 | 19.19% | 19.99% | **+0.80 pp** | 20.95% | 21.49% | **+0.54 pp** |
| 引用抽取 | 8.27% | 14.86% | **+6.59 pp** | 9.83% | 15.34% | **+5.51 pp** |

### 结果解释

- 页面生成原有隐式复用已经较高，新方案继续提升，但增量较小。
- 引用抽取把稳定候选集合与动态 chunks 分离，收益明显，是最能直接证明本轮设计有效的阶段。
- 整体热运行 +8.51 pp 还包含候选抽取在五分钟窗口内取得的高隐式命中，不能全部归因于显式断点。汇报直接收益应优先使用页面生成和引用抽取两行。
- 每轮 28 次调用全部成功，其中页面生成 16 次、引用抽取 9 次。

### 如何验收

1. 使用最终 Tag 启动后端，选择同一知识库和同一文档。
2. 连续运行两轮 Wiki 生成，记录每轮 UTC 时间窗。
3. 在 `model_call_records` 中筛选 `purpose LIKE 'wiki%'`。
4. 分别对全部、`wiki_page_modify`、`wiki_chunk_citation` 聚合 `SUM(cache_read_tokens)/SUM(prompt_tokens)`。
5. 查看逐调用记录：页面稳定前缀应呈现首请求写入、后续页面读取；引用抽取应呈现每轮首批写入、后续 chunk 批次读取。

## 九、功能七：Wiki 实体、概念和连接结构评测

### 评测范围

Wiki 评测从固定文档生成隔离临时 Wiki，再从两个层面评分：

1. 节点覆盖：实体和概念先按规范名称精确匹配，未命中的节点再用 Embedding 做语义匹配。
2. 连接结构：在已匹配节点之间比较 Wiki 页面有向连接，计算连接准确率、召回率和 F1，并列出正确、缺失、多余、不可评分连接。

Wiki 数据生成需要 Chat 模型；评分阶段只使用名称规则、Embedding 和确定性集合运算，不使用 Chat 模型裁判。该功能是用户主动运行的实验能力，不加入 CI 门禁。

### 页面验收

1. 打开“设置 → 评测中心 → 知识图谱评测”。
2. 选择数据集、Wiki 生成模型、语义匹配模型和阈值。
3. 点击开始，观察导入文档、生成 Wiki、节点评分、图评分、保存报告和清理资源阶段。
4. 完成后查看实体、概念、总体覆盖率及匹配数量。
5. 查看连接准确率、召回率、综合分数和正确/缺失/多余连接。
6. 下钻节点匹配方式与边明细，分别下载 JSON 和 Markdown 报告。
7. 刷新页面，从历史记录重新打开，确认结果仍在且临时知识库已清理。

### 通过标准

- 超过 Provider Batch 限制的节点标签会自动分批，不再产生“batch size larger than 20”错误。
- 节点、连接、生成开销和评分开销分开展示。
- 评分 Embedding 调用不会计入“文档向量化复用率”。
- 失败时记录失败阶段和错误，清理临时资源。

## 十三、已知问题和边界

1. Wiki 评测是手动实验功能，真实运行会产生 Chat 模型费用，不作为 CI 门禁。
2. Embedding 缓存默认关闭；SQL 持久缓存尚未提供适合长期大规模生产的完整租户配额和 TTL 治理。
3. 模型费用依赖管理员预先配置单价；未配置时显示“未配置”，历史价格不追溯修改。
4. Wiki Prompt Cache 的实际比例取决于 Provider 能力、缓存有效期、请求间隔和输入稳定性；不支持缓存的模型不会获得相同收益。
5. 使用真实模型执行 GitHub CI 需要配置 `WEKNORA_EVAL_HOST`、`WEKNORA_EVAL_TOKEN` 等 Secrets，并为目标分支启用保护规则。
6. 解析器横评中只有当前环境可用的 builtin 和 anydoc 产生质量分，其余引擎需要对应服务或凭据后才能完成真实横向对比。
7. Vite 生产构建存在上游已有的大体积 chunk 警告，但构建成功，不影响本次功能。
