# 可复现评测 Runner（课题三 WP2）Spec

> 状态：待审批（2026-09-01）
> 课题：腾讯犀牛鸟 · WeKnora 开源训练营 课题三「质量评测基线与成本可观测」
> 工作包：WP2 可复现 Runner（WP1 评测持久化已完成）

## 背景

WP1 已经让每次评测运行落到 `evaluation_runs` 表，并保存配置快照、`config_hash`、版本签名与历史列表接口。但目前仍缺少让评测结果可复现、可进 CI 的最后一公里：

- 发起评测只能直接调用 HTTP API，`dataset_id` 目前被服务端忽略，任何 ID 都加载同一个 `dataset/samples` 数据集；
- 检索与生成参数全部来自服务端环境配置，调用方无法用一份配置文件固定 TopK、阈值、temperature 等变量；
- 没有命令行入口、没有标准报告文件、没有稳定的进程退出码，无法被脚本和 CI 可靠消费；
- 内置数据集只有 1 个 QA 对，无法支撑有意义的基线对比。

WP2 的目标是在不重写评测链路的前提下，提供“干净环境一条命令得到可复现结果”的能力，为 WP3 基线比较器与 CI 质量门禁打基础。

## 目标

- G1：提供一条命令入口，从 YAML 配置读取运行参数，驱动一次完整评测并返回结果。
- G2：配置可以固定数据集、模型、检索参数、生成参数和执行参数，同一配置在不同时间运行产生同一 `config_hash`。
- G3：支持按 `dataset_id` 加载不同数据集，校验 5 个 Parquet 文件，计算确定性的数据集 SHA-256，并随仓库提供一个小型自定义数据集（10-30 个 QA 对）。
- G4：运行结束生成机器可读与人类可读两份报告，数据库记录、报告文件使用同一 `run_id / config_hash`。
- G5：进程退出码可以区分成功、配置/数据集错误、服务/模型不可用、运行失败/超时，供脚本和 CI 直接判断。
- G6：现有评测 API 保持兼容，已有调用方不受影响。

## 功能需求

- **F1：一条命令运行基线评测。** 用户执行 `make eval-baseline CONFIG=<配置路径>` 即可完成“读取配置 → 校验 → 发起评测 → 等待完成 → 生成报告”。同时提供可独立调用的命令行入口，支持非等待模式：只发起任务并输出任务 ID，由外部脚本继续轮询。

- **F2：YAML 配置驱动。** 配置文件中至少包含：
  - 数据集 ID；
  - Chat / Embedding / Rerank 模型（ID 或名称，留空则使用服务端默认值）；
  - 检索参数：向量阈值、关键词阈值、Embedding TopK、Rerank TopK、Rerank 阈值；
  - 生成参数：temperature、max_tokens、top_k、top_p、seed 等摘要配置项；
  - 执行参数：是否等待、轮询间隔、超时、报告输出目录。
  配置文件缺失、字段类型错误、数据集或模型不存在时，在发起任务前给出明确错误并返回对应退出码。

- **F3：按数据集 ID 加载。** `POST /evaluation` 中的 `dataset_id` 真正生效：`default` 继续加载内置 `dataset/samples`，其他合法 ID 加载仓库内对应目录的 5 个 Parquet 文件。数据集 ID 必须通过严格的安全校验（仅允许字母、数字、`-`、`_`），拒绝路径穿越。

- **F4：数据集校验与哈希。** 加载数据集时校验 `queries / corpus / answers / qrels / qas` 五个文件存在且 schema 正确，并检查引用完整性（每个问题能关联到答案与相关段落，相关段落存在于语料）。数据集内容指纹采用确定性算法：同一内容两次计算得到同一 SHA-256，内容变化后哈希变化；该哈希与样本数写入运行快照。

- **F5：模型与参数可覆盖。** 评测请求新增可选的 Embedding 模型字段，以及可选的检索/生成参数覆盖字段；服务端用请求中的覆盖值补全默认值后执行评测。未传覆盖值时行为与当前版本完全一致。

- **F6：任务轮询。** 等待模式下，Runner 轮询 `GET /evaluation?task_id=...`，以固定间隔观察状态与进度，直到 success / failed / interrupted 或超时；非等待模式只返回任务 ID。任务进入失败或中断状态时，报告包含 `err_msg` 与已完成的进度。

- **F7：标准报告输出。** 运行结束（含失败/超时）输出：
  - `evaluation-result.json`：`run_id`、`config_hash`、数据集哈希、模型信息、生效配置、版本签名、状态、进度、指标、错误摘要、复现命令、时间戳；
  - `evaluation-report.md`：人类可读的结果摘要，包含复现命令与报告生成时间。
  默认输出目录为仓库根目录 `artifacts/evaluation/`，可通过配置或命令行参数修改。

- **F8：可靠退出码。** Runner 对外退出码约定：
  - `0`：成功；
  - `2`：指标退化（本工作包仅保留编号与语义，实际比较器在 WP3 实现）；
  - `3`：配置或数据集错误（文件缺失、schema 错误、非法数据集 ID、配置无法解析）；
  - `4`：服务或模型不可用（连接失败、鉴权失败、服务 5xx、模型缺失/不可用）；
  - `5`：运行失败或超时（任务终态为 failed / interrupted，或等待超时）；
  - `130`：用户中断（Ctrl-C / SIGTERM）。

- **F9：随仓库提供演示数据集。** 新增一个 10-30 个 QA 对的小型数据集（使用仓库已有语料，不调用 LLM 生成），保证默认配置开箱即可运行，同时足以支撑 WP3 的基线对比演示。

## 非功能需求

- **N1：向后兼容。** 所有新增 API 字段均为可选；未传新字段时，`POST /evaluation` 的请求与响应、默认参数装配、`config_hash` 口径均与 WP1 保持一致。

- **N2：确定性。** 数据集哈希、配置哈希、报告中的复现命令必须是确定性的；两次相同配置的评测，`config_hash` 相同，报告字段稳定。

- **N3：敏感信息最小化。** 配置文件和报告中不得包含 API Key、endpoint 凭据、Prompt 正文、问答原文；运行快照继续沿用 WP1 的脱敏规则。

- **N4：错误可解释。** 任何失败路径都输出可读错误信息：是配置问题、数据集问题、服务不可用，还是评测运行本身失败，不能被混为一谈。

- **N5：低侵入。** 不新增数据库表，不改变评测执行链路与指标算法，不依赖 WP3 的基线比较能力。

- **N6：跨部署可用。** Runner 通过现有 API 工作，同时兼容 Lite 模式（SQLite）与标准模式（PostgreSQL），不依赖服务进程内的内存状态。

- **N7：可测试。** 配置解析、数据集校验、API 客户端、轮询与退出码映射、报告生成均有自动化测试；至少有一个端到端场景真实跑通。

## 不做的事

- **不做基线比较器与 CI workflow。** 阈值比较、基线文件管理、GitHub Actions 门禁属于 WP3；本工作包只预留退出码 `2` 的语义，不实现比较逻辑。
- **不做成本台账。** 模型调用记录、token 统计、费用估算属于 WP4。
- **不做 Embedding 缓存、Prompt 缓存实验。** 属于 WP5 / WP6。
- **不做前端页面与演示材料。** 属于 WP7。
- **不做样本级明细持久化。** 每个样本的检索结果、生成文本与单样本指标仍不落库；报告只包含聚合结果与错误摘要。
- **不做断点续跑。** 中断任务只被解释为 interrupted，不从中断点继续。
- **不改变指标算法与并发模型。** 12 项指标、检索/生成链路、样本并发执行方式全部保持现状。
- **不使用 LLM 生成数据集。** 演示数据集直接基于仓库已有语料整理，避免额外模型依赖。

## 验收标准

- **AC1（对应 F1/F7）：一条命令出报告。** 执行 `make eval-baseline CONFIG=./evaluation/configs/default.yaml`，进程以退出码 0 结束，并在默认输出目录生成 `evaluation-result.json` 与 `evaluation-report.md`。

- **AC2（对应 F1/G4）：报告与数据库一致。** `evaluation-result.json` 中的 `run_id` 与 `config_hash` 能在服务端 `evaluation_runs` 表中查到同一记录，且字段值一致。

- **AC3（对应 F3/F4/F9）：自定义数据集可用。** 新增演示数据集包含 10-30 个 QA 对；以 `dataset_id=demo` 发起评测成功，快照中的 `dataset.sha256` 与 `sample_count` 正确。

- **AC4（对应 F2/F8）：配置错误退出码为 3。** 传入不存在的配置文件、非法的数据集 ID、缺失模型字段时，Runner 在发起任务前报错并以退出码 3 结束，服务端不产生新运行记录。

- **AC5（对应 F8）：服务不可用退出码为 4。** 服务未启动、鉴权失败或接口返回 5xx 时，Runner 以退出码 4 结束。

- **AC6（对应 F6/F8）：运行失败/超时退出码为 5。** 任务终态为 failed / interrupted，或等待超时，Runner 以退出码 5 结束，报告中包含 `err_msg` 与最终进度。

- **AC7（对应 F5/N1）：参数覆盖生效且兼容。** 同一服务、同一数据集，两次运行分别使用不同 YAML 参数，数据库中的 `params` 与 `config_hash` 不同；不带新字段的原始 `POST /evaluation` 请求仍返回与之前一致的响应。

- **AC8（对应 F1）：非等待模式可用。** 使用非等待模式运行时，进程以退出码 0 结束并输出任务 ID；随后用该 ID 通过现有查询接口或等待模式仍能完成轮询与报告。

- **AC9（对应 N2）：可复现签名一致。** 相同数据集与配置连续运行两次，两次 `config_hash` 相同；报告中包含可复现命令与版本签名。

- **AC10（对应 F3/N4）：路径安全。** 尝试使用 `../`、绝对路径或包含特殊字符的 `dataset_id` 会被拒绝并返回配置错误（退出码 3），不读取仓库外目录。

- **AC11（对应 N3）：无敏感信息泄漏。** 报告、配置样例与运行快照中不出现 API Key、endpoint 凭据、Prompt 正文。

- **AC12（对应 N7）：自动化验证。** 相关单元测试通过；`go build` / `go test` 覆盖新增代码；端到端场景在真实服务（Lite 模式即可）上完整跑通并记录证据。

## 已确认的取舍（需求澄清记录）

1. Runner 的“一条命令”以 `make eval-baseline CONFIG=...` 为对外入口；底层命令入口同时存在，便于脚本直接调用。
2. YAML 中的模型与参数通过新增的可选 API 字段传给服务端，由服务端完成默认值补全与 `config_hash` 计算，避免 Runner 与服务端配置口径不一致。
3. 自定义数据集放在仓库 `dataset/` 目录下，复用现有数据集服务与 Parquet 格式；`default` 继续指向 `dataset/samples`。
4. 退出码采用本工作包约定的 0/2/3/4/5/130，与 Runner 的 CI 场景强绑定；该约定会写入 Runner 帮助与报告，避免与通用 CLI 退出码混淆。
