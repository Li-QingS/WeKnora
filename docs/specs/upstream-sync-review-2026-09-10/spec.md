# 上游同步、评测功能复核与架构 Review Spec

> 状态：已自审通过（2026-09-10）

## 背景

当前开发分支包含 RAG 评测、Wiki 评测、模型调用账本、模型价格和 Embedding 缓存等定制功能。腾讯上游 `main` 持续更新，需要先合并最新代码，再确认定制功能没有因上游变化退化，并对实现质量及关键技术选型做一次有证据的复核。

## 目标

- G1：当前开发分支包含腾讯 `upstream/main` 的全部最新提交。
- G2：重新验证 RAG/Wiki 评测、模型用量与 Embedding 缓存的功能完整性。
- G3：Review 定制代码的正确性、并发、持久化、隔离、资源清理、前端交互和迁移兼容性。
- G4：明确 Embedding 缓存使用 Redis、SQL 或分层缓存的适用性，并让实现与结论一致。
- G5：直接修复审计中发现的明确问题，提供可复现的验证证据。

## 功能需求

- F1：拉取腾讯源仓库最新 `main`，合并到当前开发分支，并保留双方提交历史。
- F2：合并后确认上游为当前分支祖先，记录 ahead/behind、冲突和迁移编号情况。
- F3：逐项核对已有 Spec、前后端入口、路由、服务、仓储、迁移和测试，形成完成/部分完成/缺失矩阵。
- F4：检查 Wiki 评分是否只使用名称匹配、Embedding 与确定性图比较，生成阶段和评分阶段调用边界是否清楚。
- F5：检查模型调用日期、成本、缓存统计和评测运行的页面/API/数据库语义是否一致。
- F6：检查 Embedding 缓存的键、租户隔离、模型隔离、并发写入、容量、淘汰、故障降级和多实例行为。
- F7：发现可在本轮安全修复的问题时补实现及必要测试；无法在无真实外部依赖条件下验证的项目明确列为运行验收项。
- F8：输出更新后的 review 文档，记录技术选型、问题严重度、修复状态和剩余限制。

## 非功能需求

- N1：合并不改写腾讯上游历史，不使用 rebase 或 force push。
- N2：缓存故障不得阻断正常 Embedding 调用；跨租户、跨模型、跨维度不得误命中。
- N3：持久化方案须兼容 PostgreSQL 与 Lite/SQLite，并说明多实例一致性和清理成本。
- N4：结论以代码、测试、数据库或真实命令输出为证据。
- N5：Wiki 实验评测仍保持手动触发，不加入 CI 质量门禁。

## 不做的事

- 不重写现有 RAG 或 Wiki 指标定义。
- 不因理论上的扩展需求引入新的基础设施。
- 不执行生产部署或生成模型付费评测。
- 不清理用户已有历史评测或模型调用数据。

## 验收标准

- AC1：`git merge-base --is-ancestor upstream/main HEAD` 成功且 behind 为 0。
- AC2：迁移序列没有编号冲突，PostgreSQL 与 SQLite 升级测试通过。
- AC3：前端测试、类型检查、生产构建以及 Go 全仓测试和静态检查通过。
- AC4：RAG/Wiki 页面、接口和服务调用链均有真实入口；Wiki 节点与连接结果可下钻。
- AC5：Embedding 缓存选型有明确结论，且键隔离、并发、重启复用、失败降级和清理策略均有实现或明确限制。
- AC6：review 文档列出所有发现、已修复项和仍需真实环境验证项。
