# Change 2 验证结果：qwen 前缀上限未见提升

## 改动内容

`wiki_page_modify` 把不依赖页面标题/slug 的固定规则整体移到
`<page_metadata>` 之前，使稳定前缀更长。

## 改造后运行（第七、八次）

| 运行 | wiki_page_modify calls | cache_read | cache_miss | 命中率 |
| --- | ---: | ---: | ---: | ---: |
| 第七次 | 16 | 23552 | 142626 | 14.17% |
| 第八次 | 16 | 18944 | 150162 | 11.20% |

对照组 `wiki_chunk_citation`：

| 运行 | cache_read | cache_miss | 命中率 |
| --- | ---: | ---: | ---: |
| 第七次 | 7424 | 62428 | 10.63% |
| 第八次 | 7296 | 63384 | 10.32% |

## 结论

- 改造前 `wiki_page_modify`：8.08%-14.05%；
- Change 1：9.17%-11.22%；
- Change 2：11.20%-14.17%；
- 结果仍处于原波动范围，没有出现显著且稳定的提升。

更关键的观察：

- 单次调用 `cache_read` 最大值仍为 2304，没有因为固定指令前置而变大；
- 说明 qwen 当前返回的缓存命中上限没有扩展，聚合命中率变化主要来自
  命中的次数和随机波动，而不是稳定前缀长度增加。

## 建议

继续调整 `wiki_page_modify` Prompt 顺序，在当前 qwen 环境下很难观察到收益。
可选的下一步：

1. 检查 qwen 对单次 prefix cache 的长度上限；
2. 用支持更长前缀缓存的模型（Anthropic/OpenAI 等）做同一实验；
3. 或把 WP6 结论定为“当前模型未观察到稳定收益，保留可观测性与已有
   cache-friendly Prompt，不再扩大改造范围”。
