# 评测运行持久化（课题三 WP1）Spec

> 状态：已批准（2026-08-29，逐段确认）
> 课题：腾讯犀牛鸟 · WeKnora 开源训练营 课题三「质量评测基线与成本可观测」
> 工作包：WP1 评测持久化（Must 级，后续 WP2 Runner / WP3 CI 门禁 / WP4 台账均依赖本工作包）

## 背景

WeKnora 已具备完整的 RAG 评测能力：通过 `POST /evaluation` 创建评测任务，自动构建临时知识库、灌入数据集、并行执行检索+生成链路并计算 12 项指标（Precision/Recall/NDCG/MRR/MAP + BLEU/ROUGE）。数据库迁移中已建好 `evaluation_runs` 表（PG 000088 / SQLite 000013，含状态、进度、参数、指标字段和租户索引），但目前没有任何代码使用它——评测任务全部保存在服务进程的内存 map 中。这导致：

- 服务重启后所有评测任务和结果永久丢失，运行中的任务变成"幽灵"（无记录、无法恢复、无法解释）；
- 无法查看历史评测记录，无法对比两次运行的指标变化；
- 评测结果无法作为 CI 质量门禁和成本分析的数据基础（课题三后续工作包的前提）。

## 目标

- G1: 评测任务的完整生命周期（创建、进度、指标、失败原因）持久化到 `evaluation_runs` 表，重启后历史记录可查询、不丢失。
- G2: 服务重启时能识别中断的运行中任务，并将其标记为可解释的终态（interrupted），而不是永远显示 running。
- G3: 每次运行保存规范化后的配置快照（数据集、模型、检索/生成参数）与版本签名（应用版本、代码版本），使历史结果可解释、可复现。
- G4: 提供按租户隔离的历史评测列表查询能力，为后续一键 Runner 和 CI 门禁（WP2/WP3）提供数据基础。
- G5: 现有评测 API 的请求/响应格式保持兼容，不破坏已有调用方。

## 功能需求

- **F1：任务创建即落库。** 用户发起一次评测时，系统在返回任务 ID 的同时，把这条运行记录写入持久化存储，初始状态为"等待执行"。记录包含：所属租户、数据集标识、用户指定的模型与知识库参数、创建时间。从这一刻起，即使服务立刻重启，这条任务也能被查到（重启后按 F4 处理）。

- **F2：执行过程进度可见且持久。** 评测执行期间，状态从"等待"流转为"运行中"，总样本数、已完成样本数、实时指标随执行推进持续更新到持久化存储。用户在任务执行的任意时刻查询，都能看到与内存中一致的进度。

- **F3：终态结果完整保存。** 任务成功时，最终 12 项指标和完整的有效配置（见 F6）一并保存；任务失败时，保存失败状态和可定位原因的错误信息。已到达终态（成功/失败/中断）的记录不可再被修改，历史结果永远是当初的样子。

- **F4：重启后中断任务可解释。** 服务启动时扫描持久化存储，凡处于"等待/运行中"且心跳已过期的任务，统一标记为"已中断"并记录中断时间。用户查询这类任务时，能明确看到"它因服务重启而中断"，而不是永远停在"运行中"。首版不提供从断点续跑；用户可对同一配置重新发起一次新运行。

- **F5：历史运行列表查询。** 提供按租户隔离的历史评测列表能力：按创建时间倒序、支持分页、可按状态筛选。列表项包含任务 ID、数据集、状态、进度、核心指标、创建/完成时间。任何租户只能看到自己的记录。

- **F6：配置快照与版本签名。** 每次运行保存一份"规范化后的完整有效配置"——不只是用户传入的四个参数，而是默认值补全后的最终生效配置（数据集标识与内容哈希、Chat/Embedding/Rerank 模型标识、检索阈值、生成参数等），以及版本签名（应用版本号、代码提交标识、工作区是否有未提交改动）。同时保存该配置的规范化哈希，使"同一配置的两次运行"可以被识别和对比。快照中不包含任何密钥、endpoint 凭据等敏感信息。

- **F7：运行中心跳。** 任务执行期间按固定间隔更新"最近一次心跳时间"，作为 F4 判断"进程已死"的依据。心跳间隔与过期阈值是固定配置，不对用户暴露。

- **F8：现有接口行为兼容。** 现有"发起评测"和"按任务 ID 查询结果"两个接口的请求/响应结构不变；区别仅在于重启后按任务 ID 查询依然能返回结果（从持久化存储读取），而不是报"任务不存在"。

## 非功能需求

- **N1：双数据库兼容。** 所有持久化读写必须同时在 PostgreSQL 和 SQLite（Lite 模式）上工作，表结构变更走两套迁移（`migrations/versioned` + `migrations/sqlite`），且不破坏现有的"SQLite 迁移必须覆盖 versioned 迁移"的守卫测试（`internal/database/migration_sqlite_versioned_schema_test.go` 的登记表需同步更新）。

- **N2：租户隔离。** 所有读写路径必须带租户边界，任何接口都无法跨租户读取或修改评测记录；该约束需要有自动化测试覆盖（A 租户的任务 ID 拿到 B 租户查询，返回"不存在"而非数据）。

- **N3：写入开销可控。** 持久化不能显著拖慢评测主链路：进度更新采用合理粒度（按样本完成批量或按固定间隔），而非每样本多次写库；评测总耗时相对当前内存实现的增长应控制在 5% 以内。

- **N4：并发安全。** 评测本身是并发执行多个样本的，进度/指标的持久化更新在并发下不产生竞态（不丢更新、不写入错乱状态）；同时多个评测任务并行运行互不干扰。

- **N5：失败不放大。** 持久化写入失败时，优先保证错误可见（记录日志 + 任务标记失败并保存原因），不允许出现"评测实际跑完了但记录丢失或状态停在 running"的无解释状态；数据库不可用时不应导致整个服务无法启动（评测功能不可用即可，其他功能不受影响——启动时的中断标记扫描失败只记日志）。

- **N6：敏感信息最小化。** 持久化内容默认不含 API Key、endpoint 凭据、Prompt 正文、问答原文；模型与配置快照只含解释结果所必需的语义参数。

- **N7：可观测性。** 关键状态流转（创建、开始、完成、失败、中断标记）有结构化日志；列表与详情接口的响应时间在中等数据量（单租户数千条记录）下保持正常分页查询水平，不随历史总量退化（依赖已有索引）。

## 不做的事

- **不重写评测链路。** 评测的执行流程（建临时知识库、灌语料、并发跑样本、算 12 项指标）、指标算法、并发模型全部保持现状，本期只把"状态与结果存哪"从内存换成持久化存储，并加上快照和恢复逻辑。

- **不做断点续跑。** 被中断的任务只标记、不从中断的第 N 个样本继续执行；想重跑就发起一次新运行（计划第 3.7 节明确建议的取舍，精确续跑留作后续增强）。

- **不做一键 Runner / 命令行工具。** 评测的发起入口仍是现有 HTTP API；`make eval-baseline`、配置文件驱动、报告导出属于 WP2。

- **不做 CI 质量门禁。** 指标基线文件、阈值比较器、GitHub Actions 工作流属于 WP3；本期只保证数据已落库、格式可被未来比较器消费。

- **不做成本台账与费用。** 模型调用记录表、token 统计、费用估算属于 WP4；本期 F6 的快照只记录模型语义参数，不采集 token 用量。

- **不做 Embedding 缓存、Prompt 缓存实验。** 属于 WP5/WP6。

- **不做前端页面。** 历史列表和详情只提供后端接口；可视化页面属于 WP7。前端现有评测入口（如有）的行为保持不变。

- **不做样本级明细持久化。** 每个样本的检索结果、生成答案、单样本指标（计划 3.6.2 的 evaluation_samples）本期不存；只存聚合结果。失败样本的调试当前仍靠日志，样本明细表留作后续增强（它也是 WP3"样本级守护"的前提，到时再建）。

- **不修改既有评测 API 的契约。** 请求参数、响应字段、错误格式全部不变（F8）；新增的列表接口是新端点，不动旧端点。

- **不做评测资源的保留策略。** 临时知识库的创建与清理逻辑维持现状；因中断而残留的临时知识库如何回收，本期只记录其 ID 便于追踪，不实现自动清理。

## 验收标准

- **AC1（对应 F1/F8）：创建即持久。** 通过现有 `POST /evaluation` 发起评测，接口返回的任务结构与之前一致；任务返回后立即查询数据库，`evaluation_runs` 表中存在对应记录，状态为 pending，租户、数据集、参数字段与请求一致。

- **AC2（对应 F2）：进度持久可见。** 评测执行期间多次调用 `GET /evaluation?task_id=xxx`，能看到状态变为 running、finished 计数递增。进度变化在数据库中可查，而非仅在内存。

- **AC3（对应 F3）：终态完整落库。** 一次评测成功完成后：数据库记录状态为 success、12 项指标齐全、finished == total；人为制造一次失败（如填入不存在的模型 ID 触发执行失败），记录状态为 failed 且 err_msg 包含可定位的失败原因。终态记录在此后的任何操作中不再被修改。

- **AC4（对应 F4/F8）：重启不丢、中断可解释。** 在一次评测运行中重启服务，重启后：(a) 用同一 task_id 查询，返回状态为 interrupted 及中断时间，而非"任务不存在"或永远的 running；(b) 该次运行已写入的进度（finished/total）保留可见；(c) 对同一数据集重新发起评测，生成一条全新的运行记录，与中断记录互不覆盖。

- **AC5（对应 F5）：历史列表可用且隔离。** `GET /evaluation/runs`（新端点）返回当前租户的运行列表，按创建时间倒序、支持分页参数、支持按状态筛选；列表项包含 ID、数据集、状态、进度、核心指标、创建/完成时间。

- **AC6（对应 N2）：租户隔离有测试。** 自动化测试验证：租户 B 的上下文查询租户 A 的 task_id，返回"不存在"类错误；列表接口在租户 B 下不包含租户 A 的任何记录。

- **AC7（对应 F6）：快照可解释、可对比。** 成功运行的记录中包含：规范化后的完整有效配置（默认值已补全）、该配置的规范化哈希、应用版本、代码提交标识与 dirty 标记；用同一配置连跑两次，两条记录的 config 哈希相同；快照中不出现任何 API Key 或 endpoint 凭据（有针对此的测试或检查）。

- **AC8（对应 F7/F4）：心跳机制生效。** 运行中的任务其 heartbeat 字段随时间更新；测试中将心跳时间人为改旧再执行启动扫描，任务被正确标记为 interrupted。

- **AC9（对应 N1）：双库迁移一致。** 新增的表结构变更同时存在 PG 与 SQLite 两套迁移；`go test ./internal/database/...` 全部通过（含现有守卫测试，登记表已同步更新）；SQLite 模式下从零建库 + 从旧版本升级两条路径均验证通过。

- **AC10（对应 N3/N4）：性能与并发。** 并发单元测试（`go test -race`）通过；同一数据集在持久化实现与当前内存实现下各跑一次，总耗时差异在 5% 以内（本地基准对比，结果记录在 PR 描述中）。

- **AC11（对应 N5）：存储故障有解释。** 测试中模拟写入失败，评测任务被标记为 failed 并带原因，不出现无解释的 running 悬停；启动扫描遇到数据库不可用时仅记录日志，不影响服务启动。

## 已确认的取舍（需求澄清记录）

1. 中断任务使用独立的新状态 `interrupted`，与 pending/running/success/failed 并列，不复用 failed。
2. 模型配置快照记录模型 ID、名称、provider、关键语义参数，不存 API Key 与 endpoint。
3. 历史列表首版只做状态筛选 + 时间倒序分页，不做按指标排序/搜索（留给 WP7）。
