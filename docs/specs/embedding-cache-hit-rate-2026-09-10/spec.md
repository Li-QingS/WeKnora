# Embedding 缓存命中率优化 Spec

> 状态：已自审通过（用户已授权自主设计与开发）

## 背景

当前 SQL 缓存已产生 14,204 次持久复用，但 11,119 条记录中有 7,227 条仅使用一次。缓存键按原始字符串精确哈希，换行符、文件 BOM、首尾空白和行尾空格都会形成新键；并发的同一查询在首次结果写入前也会重复调用 Provider。

回退基线固定为远端 tag `cache-hit-baseline-20260910`，目标提交为 `e4c51bf8`。

## 目标

- 对语义等价的保守格式差异复用同一向量。
- 兼容并逐步提升已有精确键缓存，不要求清空或一次性迁移。
- 合并同一进程内并发的相同单条 Embedding 冷请求。
- 在模型用量页面展示规范化命中和并发合并数据。
- 用 EnterpriseRAG 项目语料输出可复现的优化前后结果。

## 功能需求

- F1：规范化 UTF-8 BOM、Unicode NFC、CRLF/CR、行尾水平空白和文本首尾空白。
- F2：Provider 接收规范化后的文本，使同一缓存键始终代表同一输入。
- F3：非规范输入先查规范键；未命中时回查旧版原文键，命中后写入规范键完成惰性迁移。
- F4：Batch 按规范键去重，同时兼容每个原文的旧键回查。
- F5：相同租户、模型、维度、命名空间和文本的并发单条冷请求只执行一次 Provider 调用；每个调用方获得独立向量副本。
- F6：缓存或合并机制失败不阻断原有 Provider 路径，不跨租户、模型或向量空间复用。
- F7：统计普通缓存命中、规范化命中、批内/并发请求合并、未命中和 Provider 调用。
- F8：提供固定语料格式漂移 benchmark 和并发 benchmark，记录输入数、命中率及 Provider 调用变化。
- F9：缓存统计按调用用途区分，至少识别文档向量化与 Wiki 评测；Wiki 评测标签不得计入文档向量化复用率。
- F10：模型用量页面主展示文档上传、重解析和重建索引产生的向量复用，并明确列出该指标包含与排除的范围。

## 非功能需求

- PostgreSQL 与 SQLite 存储结构保持兼容，本轮不新增迁移。
- 不引入新的基础设施；Redis 不参与本轮实现。
- 规范化保持保守，不折叠正文中的空格、段落或 Markdown/代码缩进。
- 默认缓存关闭策略保持不变。

## 验收标准

- AC1：基线 tag 已推送，能够用明确命令恢复。
- AC2：旧版精确键可命中并惰性提升到规范键。
- AC3：格式变体第二次访问命中规范缓存，向量结果一致。
- AC4：32 个并发相同冷请求最多调用 Provider 一次。
- AC5：格式漂移场景的缓存命中率至少提高 25 个百分点，Provider 输入至少减少 40%。
- AC6：Go 全仓测试、vet、build，以及前端测试、类型检查和生产构建通过。
- AC7：结果报告明确区分可复现 benchmark 与真实线上数据。
- AC8：执行相同缓存输入时，文档索引调用只增加文档向量化统计，Wiki 评测调用只增加 Wiki 评测统计。
- AC9：模型用量页面的文档向量化表不受 Wiki 评测标签的命中或未命中影响，并有可见口径说明。
