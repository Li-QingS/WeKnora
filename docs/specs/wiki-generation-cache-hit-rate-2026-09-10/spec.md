# Wiki 生成缓存命中率优化 Spec

> 状态：实现及验收完成（用户已明确授权自主设计、开发和验收）

## 背景

当前 Wiki 已依赖模型服务商的 Prompt/Context Cache，并记录 `cache_read_tokens`、`cache_write_tokens` 和 `cache_miss_tokens`。真实热运行中，全部 Wiki 调用命中率为 16.46%，页面生成 `wiki_page_modify` 为 20.95%，引用抽取 `wiki_chunk_citation` 为 9.83%。

当前 Wiki 模型位于阿里云百炼 Workspace OpenAI 兼容地址，但模型配置为 `generic`，因此通用 Chat 层没有注入阿里云显式缓存的 `cache_control`。页面生成和引用抽取虽然已把共享内容放在前缀，也没有在共享前缀结束处设置显式缓存断点。

开发前版本固定为远端 tag `wiki-generation-cache-baseline-20260910`，目标提交为 `b17f686e`。

## 目标

- 让阿里云百炼兼容端点按 Provider 能力使用显式 Context Cache，不绑定具体模型名。
- 让使用缓存路由键的 Provider 复用同一套 Wiki 稳定前缀指纹。
- 在 Wiki 页面生成和引用抽取的共享前缀末尾设置精确缓存断点。
- 保留动态页面、Chunk 和现有内容的原始语义与顺序。
- 用固定结构测试和真实 Wiki 重跑量化修改前后的缓存 Token 命中率。

## 功能需求

- F1：识别可信的 `*.maas.aliyuncs.com` Workspace 兼容端点，并按端点能力启用 `cache_control`，不维护模型名白名单。
- F2：页面生成把“系统规则 + 共享文档上下文 + 固定编辑规则”作为稳定缓存消息，页面元数据、已有内容和新增证据保持在后续动态消息。
- F3：引用抽取把“固定规则 + 同文档候选实体/概念”作为稳定缓存消息，每一批 Chunks 保持在后续动态消息。
- F4：保留系统消息、工具和其他对话消息的默认缓存断点；同一消息已有指定稳定边界时不再标记动态尾部，单次请求总断点不超过服务商上限。
- F5：首个同前缀页面请求完成后再放行并发请求，以满足服务商“响应后缓存才创建”的约束。
- F6：非阿里云自定义端点保持现有请求结构；OpenAI、Azure OpenAI 和 OpenRouter 使用稳定前缀指纹作为缓存路由键。
- F7：缓存 Token 用量继续进入模型调用台账和现有前端统计。

## 非功能需求

- 不新增数据库表和迁移。
- 不持久化或复用模型输出，Wiki 内容仍由模型逐次生成。
- 缓存断点只在 Provider 传输适配层改变消息边界，不修改发送给模型的文本内容和顺序。
- 显式缓存使用服务商默认 5 分钟有效期，不发送阿里云不支持的长 TTL。

## 不做的事

- 不把生成结果存入 Redis 或 SQL。
- 不承诺不同模型、不同租户或不同文档之间复用动态内容。
- 不用结构估算替代真实服务商返回的 `cached_tokens` 验收数据。

## 验收标准

- AC1：回退 tag 已推送且准确指向 `b17f686e`。
- AC2：带有效缓存断点的百炼 Workspace Wiki 请求不论模型名都按端点能力带有显式 `cache_control`；普通 generic 端点保持不变。
- AC3：页面生成的共享前缀断点位于 `<page_metadata>` 之前，引用抽取断点位于 `<chunks>` 之前。
- AC4：断点前后文本拼接与原始 Prompt 逐字节一致，页面生成消息角色不变。
- AC5：真实热重跑的页面生成或引用抽取读取复用率（`cache_read_tokens / prompt_tokens`）高于当前基线，并保存逐调用证据；如服务商结果没有提升，报告必须保留真实负结果。
- AC6：相关单元测试、竞态测试、全仓测试、vet、build 和前端检查通过。
